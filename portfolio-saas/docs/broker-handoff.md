# Legacy Celery broker handoff

Production still uses Redis DB 2 for both task messages and disposable results. The new Compose file has a separate Redis 7.2 broker with AOF and `noeviction`. On 2026-09-26 the old `archive` queue held 101 messages while its worker was paused, and `codal` held 200 messages without a worker. The default drain cutover must therefore abort before stopping the API.

A fresh read-only preflight at 2026-09-27 07:22 UTC found `live=0`, `archive=207`, `codal=200`, and `unacked=0`. The archive worker was paused and the Codal worker absent; the old watchdog remained executable in root cron. The protected env had none of `BROKER_HANDOFF_MODE`, `ARCHIVE_WORKER_ENABLED`, or `CODAL_WORKER_ENABLED`, so its defaults still prevent this cutover. The September 27 encrypted database dump has a same-hash off-host Mac copy and matching VPS receipt. These are observations, not an authorization to merge or run the copy; repeat the preflight immediately before cutover.

`scripts/copy_celery_queues.py` is a **prepared, unexecuted production handoff option**. It copies the raw Redis lists `live`, `archive`, and `codal` into an empty broker without parsing task arguments, changing order, deleting the old lists, starting workers, or making provider calls. It refuses unacknowledged tasks, unexpected queue lists, an occupied target, or a target without AOF and `noeviction`. It checks length and SHA-256 of every message before and after the copy, forces a target disk snapshot, then writes a new mode-0600 receipt containing counts and hashes only. An isolated two-Redis test covers exact binary payloads, source preservation, duplicate-target refusal, and unacknowledged-task refusal.

The copy does **not** itself make a cutover safe. Beat, API producers, and every old worker must be stopped after in-flight tasks finish; otherwise a new message could arrive while copying. The target's workers must stay stopped until the receipt is checked. Once any new worker starts consuming, restarting an old worker against the preserved source lists can duplicate work. A failed copy leaves the target unsuitable for cutover; clear only that isolated target after confirming the source remains intact. Never delete the old queues as a shortcut.

The draft `scripts/deploy.sh` now has an explicit `BROKER_HANDOFF_MODE=copy` path. For the current live state, set `BROKER_HANDOFF_MODE=copy`, `ARCHIVE_WORKER_ENABLED=0`, and `CODAL_WORKER_ENABLED=0` in the protected production env **before merging**, so the normal CI deploy runner takes the copy path. A process environment override remains possible for a manual run; an absent setting defaults to `drain` and safely aborts against the current backlog. The copy path builds images and takes the database backup, starts only the empty durable broker, stops old producers and running workers, checks/copies the frozen queues, and saves a mode-0600 host receipt. A copy failure restarts only services that were running before the attempt; the intentionally paused archive container stays paused. After migration but immediately before starting the new workers, it rereads both brokers and refuses a source or target queue that differs from the receipt. The new stack starts with both paid archive and Codal consumers scaled to zero. The production queue has not been copied or drained by this work.

The copy receipt is a pre-migration rollback boundary. If migration fails after the copy, the script does **not** blindly restart an old image against a changed schema; restore and recovery need operator review. `CODAL_ENABLED` controls scheduling separately from `CODAL_WORKER_ENABLED`, so a disabled worker can still accumulate durable queued work. Enable either worker only after source access, corrected parser, backlog, and cost policy are checked. `ops_check.sh` expects only workers enabled by the production flags.

The host price watchdog can normally restart the live worker and Beat. The VPS root crontab currently calls `/opt/apps/portfolio-saas/scripts/watchdog_prices.sh`, an older checkout outside the CI deployment directory. The current file at the *new* checkout path also lacks the lock until the merge runner resets that checkout to this branch. Therefore, before merging, save root's crontab, **remove the watchdog cron entry temporarily**, and remove execute permission from the old script. Confirm that no cron entry can invoke either unlocked copy. Set the three protected-env cutover flags while deployment is not running, then merge the exact green head. Do not point cron at the new checkout before its locked script is deployed. The copy preflight refuses an executable old watchdog. Once deployment and queue-receipt checks pass, install the root cron entry pointing to `/opt/apps/portfolio-repo/portfolio-saas/scripts/watchdog_prices.sh` and verify that this deployed file contains the shared env-file lock. The new watchdog and deploy then lock the same protected production env file: deploy holds an exclusive lock throughout the cutover; watchdog takes a shared lock and skips its restart when deployment owns the file. The Linux fake-Docker test covers both guards. Do not replace the env file inode while deployment is running. Restore the old watchdog and cron entry only if the cutover aborts before migration and the old stack is deliberately resumed.

One-time release order:

1. Repeat the read-only backup, archive, broker-queue, unacknowledged-task, disk, and old-worker checks. A missing recovery point or nonzero unacknowledged count stops the release.
2. Save root's crontab privately; remove its watchdog entry and disable the old script. Verify that neither checkout has an active watchdog cron invocation during the transition.
3. In the protected production env, set `BROKER_HANDOFF_MODE=copy`, `ARCHIVE_WORKER_ENABLED=0`, and `CODAL_WORKER_ENABLED=0`. Keep ownership `deploy:deploy` and mode `600`; make no env-file replacement while a deploy or watchdog holds its lock.
4. Merge the reviewed green head. The runner copies frozen queues, checks the source and target against its receipt again before any new worker starts, migrates, and starts the application with the live worker and Beat while keeping paid archive and Codal workers at zero. Verify the receipt, health, preserved portfolio workflows, and zero paid consumers.
5. Only after success, install the root watchdog cron entry against the new locked checkout. If the attempt aborts before migration and the old stack is deliberately resumed, restore the old watchdog configuration. After migration, stop and inspect the schema and both brokers before any rollback.

Deployment refuses the legacy-to-new-stack transition if an archive or Codal worker would be enabled but was not already running in the old stack, even if its queue is empty. These checks precede backup/build and API stop. `CODAL_ENABLED=0` alone cannot stop a worker from consuming already queued Codal jobs; the worker flag controls that boundary.

A read-only queue inspection at 2026-09-26 07:46 UTC found 200 Codal extraction messages for only 14 distinct announcement IDs. Eleven of those reports had at least one artifact not yet stored, so starting the Codal worker can still require external document downloads. The archive queue had 103 messages: 52 distinct `run_archive_state` fetches, 44 duplicate no-argument health checks, and seven other distinct maintenance jobs. The current copy utility preserves every original message; it does not silently remove duplicates. The Codal sweeper now excludes IDs already in the bounded pending queue before selecting new work, preventing a stalled consumer from repeatedly filling that queue with the same filings. Existing queued duplicates still require a controlled consumption or a separately reviewed compaction plan.

`operational_health_check` was falling through the archive task route, which explains the 44 pending copies while that worker is paused. New checks route to the live control queue; the old messages remain in the legacy broker.

This is an off-host recovery point for the old broker at that time, not a live mirror or proof that later queued messages are covered.
